3、group by 和order by 探测列数的区别

1. ORDER BY 探测（CTF/SQLi-Labs 首选）
原理

ORDER BY N：N 代表结果集的第 N 列。
MySQL 允许用数字代替列名：ORDER BY 1= 按第 1 列排序。

  • N ≤ 总列数：正常执行，页面正常回显
  • N > 总列数：抛出报错 Unknown column 'N' in 'order clause'

通过不断增大数字，报错临界点就是查询的列总数。

用法

Less1 payload：?id=1' order by 3--+
注释把源码尾部 ' LIMIT 0,1 删掉，最终执行：

优点
  1. 兼容性好，MySQL5/8 都能用，不受 ONLY_FULL_GROUP_BY 参数影响
  2. 报错信息直观，稳定，靶场通用
缺点
  1. 必须能注释截断源码后面内容，否则语法断裂（Less23 无法使用）
2. GROUP BY 探测列数（备选，现在不推荐）
原理

GROUP BY N：同样支持数字代表结果集第 N 列。

  • N ≤ 总列数：正常执行
  • N > 总列数：报错 Unknown column 'N' in 'group statement'
用法

和 order by 写法几乎一样：?id=1' group by 3--+
注释截断尾部，让 group by 成为顶层子句。

致命缺点（重点）

  1. 受 ONLY_FULL_GROUP_BY 影响极大（MySQL5.7、8.0 默认开启）

    开启后，哪怕 N 是合法列号，也直接报分组语法错误，探测直接失效。

  2. group by 会合并相同值的行，会改变返回结果行数，容易干扰页面回显。

对比汇总表

项目 ORDER BY 探测 GROUP BY 探测
探测原理 按结果集第 N 列排序，列不存在则报错 按结果集第 N 列分组，列不存在则报错
高版本 MySQL (8.0) ✅稳定可用 ❌极易被 ONLY_FULL_GROUP_BY 废掉
对结果集影响 只改变顺序，行数不变 合并重复行，改变行数
报错信息 Unknown column ... in 'order clause' Unknown column ... in 'group statement'
推荐程度 ⭐⭐⭐⭐⭐ 首选 ⭐ 仅旧版本 MySQL 备选
使用前提 都需要注释截断源码尾部，放到 WHERE 外面 同左

32

只要输入'，PHP 就会**自动加反斜杠转义变成 \'**，直接写1'会变成1\'，单引号失效，没法闭合。

数据库连接编码是 GBK，GBK 是双字节编码，两个字节算 1 个汉字。

绕过原理（重点）

你传：%df%27（URL 编码：%df + 单引号%27）

  1. PHP 收到，看到'，给它加反斜杠：%df%5c%27
  2. MySQL 以 GBK 解析：%df%5c 拼成一个合法 GBK 汉字，吃掉这个\
  3. 剩下单独的%27也就是**单引号’**，成功逃逸，用来闭合 SQL。

一句话：%df或%aa吃掉 PHP 自动添加的反斜杠，释放出单引号。

payload:
?id=0%df%27%20union%20select%201,2,group_concat(password)%20from%20users%20–+

1、在源码层面理解为什么会出现sql漏洞

将用户的输入直接拼接到sql语句，然后给数据库执行，在没有预编译的情况下，过滤不完全

2、怎么防护

预编译，就是先给数据库一个模板，然后用户的输入只会被当成普通文字，不会被当成命令执行，其中order by 的特殊情况，比如说
select * from users order by $sort
这里$sort 一开始就写进模板，后续用户的输入就会被拼接进去，引发漏洞，很多时候需要动态排序就无法避免，所以可以加白名单，指定用户输入

3、哪些场景最可能出现sql漏洞

只要用户可控输入，直接拼进 SQL 语句，就大概率会产生 SQL 注入；用占位符预编译绑定【值】才安全。
1、搜索框
2、登录页面（账号密码 POST）
3、列表分页 limit
4、表格排序 order by
5、后台删除、编辑、修改密码
6、注册、留言
7、多租户动态表切换

4、在源码层面的理解

每过一关就查看源码，理解为什么这么做，同时思考怎么做防护
这里也不知道怎么写，确实在能懂源码后整个人都通透了，其实也就是会看哪里是注入点，然后源码逻辑是什么，然后就是思考怎么写payload，符合逻辑，然后就是sql语法的问题，之前没学sql语法学起来比较吃力，现在好多了
